# 地図の余白：画面構成とデザインの再設計案

2026-10-05 / レビュー用・未実装

基準：`e7ddb6c`。復帰点：ローカルタグ `before-design-review-20261005`。
既存のアプリコード、本番サイト、データ、認証設定には変更を加えない。今回追加するのは設計資料と、架空の記録で動く画面案だけ。お問い合わせやダウンロードを実際に実行するものではない。

## 1. 今回決めること

短い言葉を自分の街に残す体験を中心に、日常の操作、管理、困ったときの案内を整理する。機能数を増やすより先に、どこに何を置き、どの場面で説明するかを決める。

推奨案は「紙のような落ち着き＋読みやすい操作部」。名称・記録本文には今の明朝体の雰囲気を残し、ボタン、日時、説明、入力にはゴシック体を使う。別案として、本文もゴシック体にした読みやすさ重視の案を比較する。地図やブランド名の変更は今回の中心にしない。

  ├ 保存先・アカウント
  │   ├ ゲスト：別の端末でも使う / 保存について
  │   └ ログイン中：現在のアカウント / 端末記録の引き継ぎ / ログアウト
  ├ 記録の管理

下部に4つ目のタブは追加しない。メニューの入口は各主要画面の右上に同じラベルで置く。歯車だけにせず「メニュー」と表示する。保存先の短い表示からも該当する説明に直接進める。

管理・ヘルプはスマホでは全幅のサブ画面、広い画面では右側のパネルを候補とする。地図・ノートの閲覧位置を維持し、「戻る」で元の位置へ戻す。長い問い合わせフォームは小さなモーダルに詰め込まない。

## 4. 各画面の設計

### 地図

- 第一の役割は、場所と自分の言葉を眺めること。
- ヘッダー、短い保存先表示、検索入口、地図、下部3操作を基本形にする。
- 現在地ボタンは地図内に文字付きで置く。ズーム、出典表示、地図の記録を覆わない。
- 「地図の中央を選ぶ」は場所を選ぶときに表示する。キーボードでも使える選択方法を残す。
- 件数は「この範囲に表示中」。上限に達した場合の案内と、位置精度の注意は必要時に表示。
- 初回は短い案内を1つだけ表示。「下の『書く』から、一言を残せます」。空の地図に架空のメモを混ぜない。
- 実地図の表示元は現行の国土地理院のまま。ラフ案の地図領域は配置確認用で、実地図の見た目を再現しない。

### 書く

- 本文を最初に置き、タイトルとタグは任意の折りたたみに残す。
- 場所未指定でも入力開始できる。未指定時の保存ボタンには、押せない理由を近くに表示する。
- 選んだ場所を小地図または位置確認部で確認。緯度経度は詳細へ移す。住所変換APIを新たに使わない。
- 完了後は短い「保存しました」。ゲストでは「このブラウザーに保存しました」と保存先を伝える。
- 閉じると下書きを残し、下書き破棄は補助操作にする。保存中・結果不明・容量不足の案内は目立たなくしない。
- 書きかけのままヘルプを開いても入力を失わず、戻る場所を維持する。

### ノート

- 日付、言葉、必要ならタイトルとタグ。管理ボタンや形式の説明を混ぜない。
- 日付を区切りにし、1件ごとの強い枠と影を減らす。短い本文にも十分な余白を与える。
- 記録を押すとまず閲覧。編集と削除は詳細から行え、一覧では左スワイプでも1件の削除ボタンを出せる（第12節）。通常時は削除を強調しない。
- 検索は入口を維持し、検索中は対象と解除方法を明示。「0件」と読み込み失敗を区別する。
- 初回の空状態は「まだ言葉がありません。散歩で見つけたことを、一言から。」。書く操作の入口を増やしすぎない。

### 記録の管理

- 対象を最初に表示：「この端末のブラウザーの記録」または「現在のアカウントの記録」。片方しか出力しないのに「すべて」と総称しない。
- メニュー名は「記録をダウンロード」。開いた先で「JSON形式。本文・場所・日時などを含みます。アプリへの読み戻しにはまだ対応していません」と説明。
- ファイル取得に必要な確認は1画面。書き出し中は進行状態、失敗時は再試行を表示し、元の記録を変更しない。
- 旧デモの取り込みは補助項目へ。サンプルを除外し、元データを残す現行仕様を維持。
- 全削除は区切った下部に置き、削除対象・戻せないこと・アカウント側と旧デモには影響しないことを明示してから最終確認。
- アカウント削除は、実行機能を用意するまでは「削除を依頼する」。即時削除できるように見せない。

## 5. 状態ごとの説明

| 状態 | 常に見せる | 必要なときに見せる |
| --- | --- | --- |
| 初めてのゲスト | 保存先：この端末のブラウザー | データ消去で失われる説明。閉じられるが設定から再読できる |
| 2回目以降のゲスト | 同じ保存先表示 | 任意のGoogleログイン案内。毎回の大きな勧誘や一定件数での強制登録はしない |
| ログイン中 | 保存先：アカウント | メニューにメールアドレス。別端末でも同じアカウントで利用できる説明 |
| ログイン後に端末記録あり | 「このブラウザーの記録を引き継げます」の短い入口 | 対象一覧・引き継ぎ先・確認チェック・実行。自動送信しない |
| 引き継ぎ済み | 通常のアカウント表示 | 設定から結果を確認。端末のコピーとアカウント側は自動同期しないことを明示 |
| 保存結果不明 | 続きを書くより「保存結果を確認」の状態を優先 | 同じ操作IDで再試行。未確定の内容を勝手に編集可能にしない |
| 地図やGPSの失敗 | 失敗内容と次にできる操作 | 手動で場所を選ぶ、地図を再読込、ヘルプ。記録なしと誤認させない |

初回説明の既読状態は、将来実装時に端末内の表示設定として扱う。記録そのものや引き継ぎ完了状態と混ぜない。「常時説明を縮める」と「重要なエラーを隠す」を混同しない。

## 6. ヘルプとお問い合わせ

FAQの最初の項目は「記録はどこに保存されますか」「同じSafariならスマホとPCで共有できますか」「Googleログインで何が変わりますか」「他の人に読まれますか」「現在地が使えません」「記録が見つかりません」「機種変更するときは」「データを削除したい」です。

お問い合わせは未ログインでも開ける。項目は種類（不具合／使い方／要望／データ削除）、本文、返信を希望する場合のメールアドレス。通常の要望に氏名やアカウント作成を要求しない。

送信完了と送信失敗を明確に区別し、失敗しても本文を残す。記録本文、位置情報、認証情報、詳細ログを自動添付しない。データ削除依頼には別途本人確認が必要で、依頼しただけで削除完了とはしない。

実装に先立って決める運用事項：受信先、誰が確認するか、現実的な返信目安、問い合わせ内容の保管・削除方針、無料枠と迷惑投稿対策。現在は未決定。架空の連絡先や返信期限を公開しない。フォームの送信先が決まるまで、本番に送信ボタンだけを追加しない。

## 9. デザインレビューと将来の受け入れ条件

ラフで確認する順番：ノートを読む → メニューを開く → 記録の管理 → ダウンロードの説明 → 戻る → 書く。初回・日常利用・ゲスト・ログイン後を混ぜず比較する。

- 通常の地図・ノートに「JSON」「全削除」「旧デモ取り込み」の操作が露出しない。

- メニューから管理・ヘルプへ進め、戻ったときに地図位置・スクロール・下書きを失わない。
- ダウンロードは既存の全件対象・検索やページングに依存しない性質を維持する。
- 引き継ぎの確認、部分成功後の再試行、アカウント変更時の送信停止を維持する。

- ログインしていない人も問い合わせに着ける。送れない状態で成功表示しない。

## 12. 記録ごとのスワイプ削除（2026-10-05 追記）

一覧の記録を左へスワイプすると、右側に「削除」を表示する。指を離した時点では何も削除しない。「削除」を押し、対象を確認してから1件だけ削除する。右へ戻す、本文をタップする、別の記録や余白を触る、Escキーを押すと操作を閉じる。開くのは常に1件まで。

### 操作の流れ

```text
通常の記録
  ├ タップ → 詳細を読む → 「この記録を削除」
  └ 左スワイプ → 右側に「削除」 → タップ
                       ↓
           日時・本文抜粋・保存先を確認
                       ↓
               キャンセル / この1件を削除
```

- 確認の見出しは「この記録を削除しますか？」。日時と本文を表示し、何を消すか判別できるようにする。長文は抜粋であることを明示する。
- 「この1件を削除」「キャンセル」を区別する。保存先はこのブラウザー／表示中のアカウント。引き継ぎ済みの別コピーや旧デモは消えないことを説明する。
- 確認をキャンセルした場合は、元の一覧・詳細と閲覧位置に戻す。一覧では削除ボタンを閉じ、元の記録にフォーカスを戻す。
- 現在の完全削除を使う段階では、確認画面に「削除すると元に戻せません」を表示する。成功していないうちに記録を消したように表示しない。
- 将来の実装では表示順の番号ではなく記録IDで対象を固定し、所有者とversionも検証する。検索・ページ追加・同時更新で別の記録を削除しない。

### 指の操作と代替操作

- 縦スクロールを優先する。わずかな横ぶれや斜めのスクロールで開かない。操作対象は一覧の記録内で、画面端のOSの戻るジェスチャーを奪わない。
- ラフの初期値は方向判定10px、横移動が縦移動の1.25倍を超えたら横操作、開閉の目安40px、表示幅88px。製品の確定値ではなく、実機の片手操作で調整する。
- 深くスワイプしても削除ボタンの表示で止まる。速度や距離だけで即削除する操作は設けない。
- スワイプ直後の指離しを本文のタップとして扱わない。削除が開いている本文をタップした場合は、まず閉じるだけにする。
- タッチ中断・画面切替・利用アカウント変更・対象の更新時は開いている操作を整理し、別の記録に引き継がない。
- PCではマウスドラッグでもラフを確認できるが、ドラッグを必須にしない。詳細画面の文字付き「この記録を削除」を維持し、キーボードや読み上げでも到達できる。
- 閉じている削除ボタンをTab移動や読み上げの対象にしない。開いた場合は、対象の言葉を含むボタン名と短い状態通知を用意する。
- 削除は赤と文字で示す。押す領域は44px以上。動きを減らす設定ではスライドの補間を省く。
- 発見性のため、初回だけ短く「左にスライドすると削除できます」と案内する。常設の削除ボタンや自動スワイプ演出は増やさない。

### 保存処理と失敗時の設計

削除中は同じ操作の重複送信を防ぎ、確認画面に進行状態を示す。失敗時は記録を残して理由と再試行方法を表示する。応答を受け取れず結果不明の場合は、既存の保存操作確認・競合処理を維持し、「削除しました」と断定しない。未完了の下書きや編集ロックがある場合も現行の保護を維持し、スワイプ操作から迂回できないようにする。

### 「元に戻す」は別段階

最初の段階は、既存の完全削除＋対象確認。今のラフには動作しない「元に戻す」を置かない。

次の段階で、ごみ箱または復元可能な削除状態を設計し、成功後の「1件削除しました　元に戻す」を検討する。完全削除後に同じ内容を新規作成するだけの疑似復元にはしない。記録ID、日時、他端末での扱い、引き継ぎ履歴、アプリ再起動後の復元、保持期間、最終消去を決めてから実装する。期限付きの通知だけに復元手段を閉じ込めず、ごみ箱からも復元できる案を優先する。

### この追記の確認項目

- 1件ずつ開く・閉じる、別の行で切り替わる。長いスワイプでも削除されない。
- 縦操作と小さな横ぶれで削除が出ず、短いスワイプは元に戻る。
- 一覧と詳細のどちらからでも同じ対象の確認に進み、キャンセルで戻れる。
- 閉じた削除ボタンはフォーカス対象から外れ、詳細からキーボードで削除確認に進める。
- 確認画面には1件の対象・保存先・取り消せないことが表示され、全削除と混同しない。
- ラフでは最終削除は無効。実データ、端末ストレージ、APIにはアクセスしない。
