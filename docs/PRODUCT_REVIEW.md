# 地図の余白：点検と次期設計

点検日：2026-10-04。対象：Git `4f97c62`、公開中の `/`・`/demo`、現在の実装とテスト。次期案であり、未実装の内容を含む。

## 1. 判断

現在は「場所付きの個人メモを保存できる」段階にある。次は「外出先ですぐ残せて、帰宅後や再訪時に読み返したくなる」体験を完成させる。優先する価値は、短い言葉が自分の街の記憶として積み重なること。

主な利用者はまず本人。日本国内、スマホ、個人非公開、費用を抑える方針を維持する。一般公開や他人との交流は今回の中心に置かない。需要評価は実装・今回の導入時のつまずきからの仮説で、利用者調査で実証したものではない。

## 2. 確認したこと・未確認のこと

- 公開デモで初期表示、既存ピンを開く、編集をやめる、実地図への切り替え、地理院タイルとラベル表示を確認した。保存・削除は行っていない。
- ピンを開くと閲覧画面ではなく編集フォームになることを実操作で確認した。
- コードで認証・保存・検索・ページング・現在地取得・表示レイアウト・DB制約を確認した。
- `npm run check` 再実行成功：lint、型検査、単体/API/DB 28件、通常ブラウザー14件、個人公開専用1件、本番ビルド。通常実行でスキップされる個人公開テストは別の環境変数で実行済み。
- 自動ブラウザーテストはSupabase・タイル・位置情報を模擬する。実スマホのGPS、通信切断、ソフトキーボード、ホーム画面起動の品質を証明するものではない。
- この点検用ブラウザーの本番画面はログアウト状態だった。本人の本番ログイン後のCRUD、メール再設定の配送は今回再検証していない。前回の実DB権限検証と、今回の画面テストを区別する。
- 同じ場所への大量投稿、51件以上の地図表示、同時編集後の復旧はコードから評価。実データの負荷測定は未実施。

## 4. 弱点と優先順位

P0は安心して使う前提、P1は日常利用の中心、P2は中心体験の確認後に追加する。

| 優先 | 問題・根拠 | 利用時の困りごと | 次期対応 |
| --- | --- | --- | --- |
| P0 | 初回登録がSupabase管理画面頼み。今回、サービス管理者とアプリ利用者の区別で混乱した | メモを始める前に離脱する | 初回セットアップ案内と、ログイン・通信障害・メール確認の説明を分ける。個人利用の一般登録停止は維持 |
| P0 | 本番フォームの下書きはReact stateのみ。`beforeunload`で警告するだけ（MemoForm:16–24） | アプリ切替・OS終了で書きかけを失う | アカウント別の端末下書き、再起動時の復元、保存状態の区別 |
| P0 | 更新・削除の応答喪失に復旧導線がない。PATCH再送は既にversionが進むと409。作成も応答喪失後に内容変更すると同じIDで409になり得る | 保存されたか分からず、重複や入力の写し直しを招く | 結果不明状態とサーバー照合。未確定操作の内容を固定して再送 |
| P1 | 980px以下で地図→フォーム→一覧の縦積み。操作場所が離れている | 立ち止まって何度もスクロールする | 地図中心＋下部シート、常に届く「ここに残す」 |
| P1 | タイトル・本文・カンマ区切りタグが常時並ぶ | 一言だけ残したいときも作業感が強い | 本文を主役にし、タイトル・タグは任意の補助入力にする |
| P1 | `MapView memos={filtered}` は取得済み一覧のみ。APIは50件単位（Notebook:87–90、api/memos GET） | 古い記録が地図にないため、記録が消えたと感じる | 一覧とは独立した地図範囲の取得。範囲件数と表示上限を明示 |
| P1 | ピン操作が直接編集、詳細閲覧がない（Notebook:87） | 思い出を読む操作と書き換える操作が混在する | まず読むシート、そこから明示的に編集 |
| P1 | 全ピンのラベルが常時表示。重なり回避なし（MapCanvas:94） | よく歩く場所ほど文字が読めない | 重なりを避けるラベル配置と密集時の集約 |
| P1 | 初期中心が固定。現在地と選択座標が一部連動。保存後も選択点が残る | 自分の街から始まらない、前の場所にうっかり保存する | 地図の閲覧位置・GPS・作成地点・閲覧メモを別の状態として管理 |
| P1 | 場所を示す情報が緯度経度中心。タイトルなしは一覧で「無題」 | どの記録か思い出しにくい | 任意の場所名、本文先頭の見出し、日付・小地図 |
| P1 | バックアップの実運用・ユーザー向け書き出しなし。削除は完全削除 | 大切な蓄積を預ける不安 | JSON書き出し、復元確認、削除取消。アプリ書き出しとDBバックアップを分ける |
| P2 | 一覧の件数は取得済み件数で、検索後も「3/3」のように見える | 全件数・検索件数と誤解する | 「検索結果」「表示中」「続きあり」を分け、必要なときのみ総件数取得 |
| P2 | 写真・散歩単位のまとめ・再訪管理がない | 帰宅後に整理したり次の散歩に使いにくい | 利用実績を見て、再訪保存→散歩単位→写真の順を検討 |
| P2 | 地図ズーム36px、タグ32pxなど主要44pxルールの例外 | 屋外・片手で押しにくい | 主要操作44px以上、文字拡大、フォーカス、配色・色以外の区別を実機検証 |

## 5. ユーザーが必要とするものと、使いたくなるもの

| 場面 | 最低限ほしいこと | 使い続けたくなる価値 | 設計上の注意 |
| --- | --- | --- | --- |
| 目の前で何かに気づいた | 現在地に一言をすぐ残す | 「金木犀の匂い」のような短さでも完成した記録になる | 長文・タイトル・タグを要求しない |
| GPSがずれている | 地図を動かして場所を直す | 「この角」「あの階段」を自分の言葉で示せる | 精度と取得時刻を明示。座標は詳細に置く |
| 地下・電波の弱い路地 | 入力が消えない、後で保存できる | 通信を気にせず観察に戻れる | 端末保存をクラウド保存済みと表示しない |
| 家に帰った | 今日の記録を一覧で読む | その日の散歩がひと続きの記憶に見える | 最初は日付別表示で成立させる |
| 同じ街を再訪した | 近くの過去メモを見つける | 以前の自分の言葉と出会う | 古い記録をページングで落とさない |
| 来週また歩きたい | 行きたい場所を見返す | 自分だけの次の散歩候補ができる | 星印など軽い操作で十分。自動通知は不要 |

既存のメモ帳との差は「どこで書いたか思い出せること」。一般の地図サービスとの差として育てたいのは「自分がそこで何を感じたかが残ること」。口コミ量や施設情報の網羅性を競う設計は優先しない。

## 6. 次の画面設計

### 地図ホーム

- 初回は「現在地を表示」と「地図から選ぶ」を案内。位置情報を勝手に要求しない。
- 2回目以降は最後に見ていた地図範囲を復元。GPSは利用者が押したときに更新する。
- 上部は小さなアプリ名と検索。下部は「地図」「ノート」と大きな「ここに残す」。ログアウト・詳細座標・接続設定は補助メニューへ。
- 地図の中心に選択目印。「ここに残す」を押した時点の座標を下書きへ固定する。閲覧のために地図を動かしただけでは編集中の場所を変更しない。
- ピンを押すと読むシートを開く。本文・日付・場所名を見せ、「編集」「また来たい」「その他」を置く。
- 低ズームでは密集メモを件数に集約、高ズームでは重ならない範囲で言葉を表示。選択メモの言葉を優先する。

### 書くシート

最初に見せるのは「この場所で何を見つけましたか？」の本文、場所の確認、保存ボタン。タイトルは任意、タグは候補チップ＋自由入力、場所名・日時は詳細を開いて変更する。

入力開始→端末に下書き保存→利用者が「保存」→通信中→クラウド保存完了、を別の状態として表示する。保存後は本文先頭の小さなカードを見せ、地図に戻る。場所を固定したまま続けて書く場合だけ明示的な操作を用意する。

キーボード表示中にも本文・保存操作へ届くようにする。シートはドラッグだけでなくボタンで開閉でき、閉じると起点にフォーカスを戻す。縮小画面や文字200%表示でも操作を隠さない。

### ノート

日付ごとの一覧、本文検索、タグ、任意の「また来たい」絞り込み。本文の冒頭をカードに使う。「今日の散歩」は作成日で仮にまとめ、別の日の思い出を記録したい需要が確認されたら `observed_at` を追加する。

### アカウント・データ

本人のメール、端末の下書き管理、書き出し、ログアウト、接続トラブルの案内。Supabaseという管理サービス名を通常利用の手順に出さない。ログイン画面からデモへ行けるが、ログイン後の主画面からはデモへの大きな誘導を外す。

## 7. 実装設計

### 状態と保存

- `mapViewport`（閲覧範囲）、`deviceLocation`（取得時刻・精度）、`activeMemoId`（読む対象）、`draft`（編集地点と本文）を分ける。現在の共通 `selected` に複数の役目を持たせない。
- 下書きはIndexedDBに `schemaVersion / userId / draftId / memoId / baseVersion / payload / updatedAt / operationId / state` を保存。入力変更から短い待機後とページ非表示時に保存を試す。容量不足・権限拒否・書き込み失敗を画面に通知する。
- `local_draft → sending → synced`、失敗時は `retryable`、応答喪失時は `unknown`、他端末競合は `conflict` と分ける。
- ログアウト・ユーザー切替では別ユーザーの下書きを読めない。ログアウト時は端末下書きの削除・保持を明示し、初期案は削除を標準にする。端末ストレージは端末利用者や同一オリジンのスクリプトからの機密保護を保証しない。
- 未確定POSTは送ったpayloadとIDを保持し、その内容で照合・再送する。変更した文章は別の下書きとして保全し、照合後に編集へ移す。
- PATCH/DELETEの結果不明時は本人の対象IDを再取得する。PATCHは送信内容・versionとの一致を確認し、別変更なら比較して選べるようにする。DELETE済みなら完了扱い。照合ができない状態を成功とみなさない。
- 最初は「通信回復後に利用者が再送」を実装する。自動送信キューは認証期限・競合・二重保存・他端末編集を扱える段階で追加する。

### 地図データ

- 一覧のカーソルAPIを維持し、地図用に `GET /api/memos/map?west=&south=&east=&north=&zoom=&q=` を追加する案。
- 同じ認証・所有者制約・検索正規化を通す。返すのはID、座標、短い表示文、必要な状態。全文は詳細取得時に読む。
- 地図範囲、座標、ズーム、上限を検査。初期案は範囲内200件まで個別表示。超過時は集約データと総数・`truncated` を返し、全件表示と誤認させない。日本以外を対象に広げる際は日付変更線も扱う。
- 地図移動中は取得せず、停止後にまとめる。古いリクエストを中断・無視し、同じ範囲は短時間キャッシュ。ログアウト時に本人データのキャッシュを破棄する。
- 最初は既存lat/lngと所有者条件で検証。1,000件・10,000件で実行計画を確認して索引を決める。必要になればPostGISを検討し、最初から導入を前提にしない。

### データの拡張

第一段階は既存memosを維持し、下書きだけ端末へ追加。次段階の追加候補は `place_label`（任意の自分用場所名）、`starred`、`deleted_at`。後日記録の需要があれば `observed_at`。場所名の自動取得は外部APIに依存するため最初は手入力。

削除取消は `deleted_at` と復元操作で実装する案。通常一覧・検索・地図から除外し、書き出しでは扱いを明記する。RLS・列単位grant・version更新・検索・復元テストを一緒に更新する。既存migrationを再実行せず、追加migrationで前進する。

### 費用と運用

- 地図・現在地・本文入力は既存構成で実現する。写真、施設検索、音声認識の外部サービスは次期の必須条件にしない。
- 写真を追加する場合は枚数・サイズ上限、端末での圧縮、EXIFの位置情報除去、非公開Storage・RLS、削除連動、書き出しへの含め方を先に設計する。
- 地理院タイルの出典を維持。タイルの事前大量取得・オフライン一括保存は今回導入しない。[提供元の利用案内](https://maps.gsi.go.jp/development/ichiran.html)
- ユーザー向けJSON書き出しは本人の全件をページング取得し、件数と形式のバージョンを記録する。表示中50件だけを書き出さない。CSVは表計算用の追加形式として式注入にも対応する。
- DB全体のバックアップと復元試験も別途必要。Freeプランでは定期的な外部バックアップが公式に推奨されている。[Supabase公式](https://supabase.com/docs/guides/platform/backups)
- Freeプロジェクトには低利用時の一時停止があるため、接続不能をパスワード誤りと同じ文言にしない。[Supabase公式](https://supabase.com/docs/guides/platform/free-project-pausing)
- 開発ブランチへのpushが本番に直結している。次の実装は別ブランチ・模擬データで確認し、CI成功後に本番ブランチへ反映する運用へ。プレビューに本番DBを不用意に接続しない。
- SQL Editor適用分のmigration履歴を照合し、以後の変更履歴を整える。README・VALIDATIONの公開前表現やテスト件数も更新が必要。

## 8. 実装順と合格条件

| 段階 | 作るもの | 合格条件 |
| --- | --- | --- |
| A：利用を成立させる | 実アカウントの動作確認、認証エラー整理、下書き復元、保存結果照合、書き出し | 本人のiPhoneでログイン→作成→再読込→編集→削除。アプリ切替・再起動で下書き復元。応答喪失でも二重保存なし。別アカウントへ漏れない。全件の書き出しを確認 |
| B：街で使いやすくする | 地図ホーム、書く・読むシート、本文中心入力、現在地と記録地点の分離 | 初回説明後、場所選択・本文・保存が大きなスクロールなしで完了。キーボード下に保存操作が隠れない。許可拒否・低精度でも記録できる |
| C：蓄積を役立てる | 範囲別地図取得、密集表示、日付別ノート、場所名、再訪保存、削除取消 | 51件以上でも範囲内の古い記録を見つけられる。密集時に文字が重ならない。復元した記録を検索・地図でも再表示 |
| D：実利用から選ぶ | ホーム画面追加の整備、写真、散歩単位のまとめ、施設検索 | 実際の散歩で「足りない」と確認された機能を1つずつ追加し、費用・操作数・データ保護の変化を検証 |

Aの下書き・状態管理をBの画面変更より先に設計する。Bの地図体験を出すときはCの範囲取得もそろえ、古い記録が見えない問題を残さない。期間は実機結果と範囲が決まってから見積もる。

## 9. 確かめたい利用仮説

本人が3回の散歩で利用し、各回3件程度を残して帰宅後に見返す。移動中ではなく安全な場所に止まって操作する。

1. 記録の意図ができてから短文保存まで30秒以内を目標とする（実測値ではない）。現在地の取得待ちと文字入力時間を分けて測る。
2. 文字入力以外は、現在地・書く・保存の3操作程度を目標とする。GPS拒否と場所修正は別の経路で確認する。
3. 翌日、覚えている場所や言葉から目的の記録を30秒程度で探せるか確認する。
4. 困ったときに「端末に残った」「クラウドに保存された」「再送が必要」を本人が言い分けられるか確認する。
5. 次の散歩で自発的に開いたか、写真がなくて困ったか、タイトルやタグを使ったかを聞く。

個人利用の段階では大規模な解析SDKは不要。操作時間と困った場面を短い日誌に記録する。本文・座標・メール・トークンをアクセス解析やエラーログへ送らない。見た目の好みだけでなく、記録を残せたか・再び開いたかで次の優先順位を決める。
